Individual track A / Bicep / 20 minutes

A Bicep file is a typed resource graph.

Start with inputs, derive names, declare resources, and expose outputs. A symbolic name such as store exists in the file; store.name is the deployed Azure name. The resource type and API version select the resource schema. Bicep compiles to ARM JSON; Azure Resource Manager performs the deployment.

A complete first file: storage.bicep

targetScope = 'resourceGroup'

@description('Azure region for the storage account.')
param location string = resourceGroup().location

@minLength(2)
@maxLength(8)
param prefix string = 'campus'

@allowed([
  'Standard_LRS'
  'Standard_ZRS'
])
param sku string = 'Standard_LRS'

param tags object = {
  environment: 'learning'
}

var accountName = '${toLower(prefix)}${uniqueString(resourceGroup().id)}'

resource store 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: accountName
  location: location
  kind: 'StorageV2'
  sku: {
    name: sku
  }
  tags: tags
  properties: {
    minimumTlsVersion: 'TLS1_2'
    supportsHttpsTrafficOnly: true
    allowBlobPublicAccess: false
    allowSharedKeyAccess: false
  }
}

output storageName string = store.name
output storageId string = store.id

The name combines a lowercase prefix with a deterministic suffix. Storage names must be 3-24 lowercase letters or digits; the decorators constrain length, not the character set. Use a letters-only prefix such as campus. Deterministic names avoid creating a fresh account on every repeat deployment.

SyntaxPurposeRemember
param name type = defaultInputs with optional defaultA required parameter omits the default
var name = expressionDerived valuesNot mutable program state
resource symbol 'type@version' = { ... }Declare an instanceSymbol is not necessarily its Azure name
output name type = valueReturn values to callersDo not output credentials or secrets
'${expression}'String interpolationBicep uses single-quoted strings
@secure()Protect sensitive deployment parametersDoes not make a plaintext parameter file safe

Environment values: storage.dev.bicepparam

using './storage.bicep'

param prefix = 'campus'
param sku = 'Standard_LRS'
param tags = {
  environment: 'dev'
  owner: 'learning-team'
}

using binds the parameter file to its Bicep file. Values must match parameter names and types. A native .bicepparam uses param x = value, not a type declaration. It does not use the JSON file's @ prefix in Azure CLI.

az bicep build --file .\storage.bicep
az bicep build-params --file .\storage.dev.bicepparam

Build validates language and schema and emits JSON. It does not verify permissions, quota, regional allocation or application health. Use a current CLI/Bicep combination; linked parameter-file deployments without --template-file require Azure CLI 2.53.0+ and Bicep 0.22.6+.

Types and operators you will use repeatedly

Types include string, int, bool, array, object and user-defined types. Compare with == and !=; combine conditions with && and ||; choose with condition ? yes : no; use ?? for a null fallback. Arrays use [ ... ], objects use { key: value }. Object properties do not need JSON-style commas.

type Environment = 'dev' | 'prod'
param environment Environment
var isProduction = environment == 'prod'
var storageSku = isProduction ? 'Standard_ZRS' : 'Standard_LRS'

Individual track A / Bicep / 20 minutes

Compose small modules. Let references express dependencies.

A module is a reusable Bicep deployment unit with a parameter/output contract. If another resource references an output or property, Bicep infers the deployment dependency. Use explicit dependsOn only when an actual dependency cannot be expressed by such references.

module photos './storage.bicep' = {
  name: 'photos-storage'
  params: {
    location: resourceGroup().location
    prefix: 'photos'
    tags: {
      environment: 'dev'
    }
  }
}

output photoStorageId string = photos.outputs.storageId

name on the module is its deployment name, not the storage account name. Module parameter defaults still apply when an optional value is omitted. Prefer clear contracts over passing a huge untyped configuration object everywhere. Version-pin reviewed public modules rather than silently accepting changing code.

Loops: create a collection from data

param containerNames array = [
  'photos'
  'receipts'
]

resource blobs 'Microsoft.Storage/storageAccounts/blobServices@2023-05-01' = {
  parent: store
  name: 'default'
}

resource containers 'Microsoft.Storage/storageAccounts/blobServices/containers@2023-05-01' = [for containerName in containerNames: {
  parent: blobs
  name: containerName
  properties: {
    publicAccess: 'None'
  }
}]

The collection is an array of resource declarations, not a runtime application loop. Referencing parent: store links the resource hierarchy. A child resource's type still includes its full provider/type path even when parent lets you use only the child name.

Conditions: include or omit one resource/module

param createArchive bool = false

module archive './storage.bicep' = if (createArchive) {
  name: 'archive-storage'
  params: {
    prefix: 'archive'
  }
}

output archiveId string = createArchive ? archive!.outputs.storageId : ''

The condition does not automatically apply to separately declared children. Guard references to conditional resources/modules. The ! asserts non-null here because the matching condition guards access; it is not a substitute for handling missing resources correctly.

Existing resources: reference without recreating

param existingStorageName string

resource existingStore 'Microsoft.Storage/storageAccounts@2023-05-01' existing = {
  name: existingStorageName
}

output existingId string = existingStore.id

existing does not import that resource into full lifecycle ownership or create it. Property reads can require permissions and can fail if the instance is absent. Cross-group references use an appropriate scope: resourceGroup(...).

Exercise: make a reusable two-environment module

Use the complete storage.bicep file, create dev and prod parameter files, and change only tags and SKU. Before choosing ZRS for production, verify regional support and requirements. Keep unique naming tied to resource scope. Explain why recreating the name randomly would change the deployment outcome.

Expected result: both files compile; each is bound to the same module; a repeated deployment in one group keeps the same account name. This exercise verifies composition, not that any storage redundancy setting alone satisfies a full application's recovery requirements.

Match the target scope to the deployment command.

At subscription scope, a deployment's --location stores deployment metadata; it does not override each resource's location. Use modules scoped to groups to deploy ordinary group-scoped resources from a subscription template. The combined lab shows this pattern.

The resource-group deployment sequence

$subscription = 'REPLACE_WITH_YOUR_SUBSCRIPTION_ID'
$rg = 'rg-campus-bicep-dev'
$location = 'westeurope'
az account set --subscription $subscription
az account show --query "{name:name,id:id,tenant:tenantId}" --output json
az group create --name $rg --location $location
az deployment group validate --resource-group $rg --parameters .\storage.dev.bicepparam
az deployment group what-if --resource-group $rg --parameters .\storage.dev.bicepparam
az deployment group create --name storage-dev --resource-group $rg --parameters .\storage.dev.bicepparam
az deployment group show --name storage-dev --resource-group $rg --query properties.outputs --output json

Run each line deliberately and stop on errors. Validation and what-if are management requests, not fully offline checks. What-if previews likely changes but can contain noise or unresolved expressions. It does not reserve capacity, create a rollback plan or guarantee success.

Repeatability is not magic

Stable names and declarative configuration make repeat deployments converge where APIs support it. Some properties cannot change in place. Concurrent deployments, runtime defaults, provider behavior and out-of-band edits can cause unexpected results. Review every meaningful diff.

Incremental is not "patch only"

Incremental deployments retain resources not listed in the template, but redeploy a declared resource's configuration. Omitted properties can return to defaults. Removing a declaration does not normally delete the resource. For managed deletion workflows, understand deployment stacks rather than casually switching to complete mode.

Secrets, drift and deployment history

Use secure parameters and appropriate secret retrieval mechanisms; do not store passwords in parameter files or outputs. Bicep does not require a Terraform-style local state file; ARM manages resource and deployment state. Deleting a deployment-history record does not delete the resources it created. A failed deployment can leave successfully created resources behind; rollback is not universally automatic.

Clean up the standalone Bicep sandbox

The later azd down command removes the combined azd environment, not this separately created Bicep sandbox. After any CLI exercises that use this group, inspect the explicit subscription and group below. Confirm deletion only if every resource belongs to your isolated lab. These commands are destructive and must not target a shared group.

az resource list --subscription $subscription --resource-group $rg --output table
az group delete --subscription $subscription --name $rg
az group exists --subscription $subscription --name $rg

Use the standalone values $rg = 'rg-campus-bicep-dev' and your original sandbox subscription ID, not values overwritten by a later lab. The final command should return false after deletion completes. Check for any other groups you created during module exercises and clean those up individually after reviewing their ownership.

Read an Azure command as a sentence.

Not every command has a subgroup. For example, az group show is group + verb; az storage account show adds a subgroup. Flags identify the target and configure the request. --query shapes the response; --output chooses serialization.

Inspect JSON first. Project only what you need.

Azure CLI usually returns structured JSON. JMESPath is a query language for that JSON, not an Azure resource search language or SQL. Querying command output is generally client-side; it is not proof that the server fetched fewer items.

az group list --output json
az group list --query "[].name" --output tsv
az group list --query "[].{group:name,region:location}" --output table

Individual track B / Azure CLI / 15 minutes

Successful authentication is only the first gate.

Check identity, subscription, management permission, policy, quota/capacity, data permission and network reachability separately. Contributor generally manages a storage account but does not grant blob data access. A valid token does not override a firewall.

az account show --output json
az provider show --namespace Microsoft.Storage --query registrationState --output tsv
az resource list --resource-group $rg --output table
az role assignment list --scope $groupId --include-inherited --output table
az monitor activity-log list --resource-group $rg --offset 1h --query "[].{time:eventTimestamp,status:status.value,operation:operationName.value}" --output table
az deployment operation group list --resource-group $rg --name storage-dev --output json

$groupId is the ARM ID from the previous chapter. The deployment-operation command refers to the standalone deployment name storage-dev; azd uses its own deployment names. Permissions and registration checks can themselves be denied. If the provider is unregistered, an authorized operator can deliberately run az provider register --namespace Microsoft.Storage; do not register providers casually in an unrelated subscription.

Data-plane recipe: no account keys

az storage blob list --account-name $storage --container-name 'photos' --auth-mode login --query "[].{name:name,size:properties.contentLength}" --output table

Use --auth-mode login to request Entra-based authorization instead of relying on account keys. The container must exist, your identity needs the relevant blob data role, and the endpoint must be reachable. Do not "fix" an authorization error by enabling anonymous access or embedding keys.

Automation: native commands need native exit checks

$ErrorActionPreference = 'Stop'
az account show --output none
if ($LASTEXITCODE -ne 0) { throw 'Azure CLI authentication or context check failed.' }
az deployment group what-if --resource-group $rg --parameters .\storage.dev.bicepparam
if ($LASTEXITCODE -ne 0) { throw 'What-if failed; do not deploy.' }

$ErrorActionPreference alone does not reliably convert every native executable failure into a terminating error across PowerShell configurations. Test $LASTEXITCODE immediately after az/azd. Do not swallow errors, deploy after a failed diff, or log tokens. --debug logs can contain sensitive information; review and redact before sharing.

Diagnose by evidence rather than retrying everything

AuthorizationFailed: verify principal, scope and required action. RequestDisallowedByPolicy: inspect the policy assignment and evaluated property. Allocation/quota errors: distinguish allowed quantity from regional supply. HTTP 403 on blobs: inspect data RBAC, network rules and token audience. DNS/connectivity failure: inspect the endpoint path and name resolution. Conflict: avoid concurrent changes and check provisioning state. Retry only when you understand a transient cause.

Individual track C / Azure Developer CLI / 10 minutes

An environment is configuration, not a new cloud.

Use environments for independent deployments such as dev/test/prod. azd stores local configuration under .azure; that configuration is not automatically a security boundary or a secret vault. The infrastructure must use environment-dependent names and scopes to keep resources separate.

azd auth login
azd auth status
azd env new campus-dev
azd env set AZURE_SUBSCRIPTION_ID 'REPLACE_WITH_YOUR_SUBSCRIPTION_ID'
azd env set AZURE_LOCATION westeurope
azd env list
azd env select campus-dev
azd env get-values

AZURE_ENV_NAME identifies the selected environment. AZURE_SUBSCRIPTION_ID and AZURE_LOCATION configure targeting. AZURE_PRINCIPAL_ID supplies the deploying identity's object ID for templates that require it. Infrastructure outputs are persisted as environment values, providing IDs and endpoints to subsequent commands/hooks.

azd env refresh refreshes values from deployed infrastructure; it does not recreate missing resources or deploy new code. Explicit --environment campus-dev avoids accidentally targeting the last selected environment.

Do not commit secrets or local environments. Exclude .azure/ and reviewed local artifacts in your application's ignore file. azd env get-values can print sensitive values in real projects; do not copy the complete output into shared logs. Nonsecret outputs should be the default.
Why two environment names can still collide

If the Bicep file uses a hard-coded resource group or account name, different local environments can point at the same Azure resources. Derive names using environment and scope, verify outputs and resource discovery, and set separate subscription boundaries where required. Environment labels alone do not grant or isolate access.

Individual track C / Azure Developer CLI / 10 minutes

Hooks are executable code, not harmless metadata.

Hooks run at lifecycle boundaries. Project hooks cover commands; service hooks cover an individual service's stages. Keep hooks small, deterministic, reviewed and failure-visible. Avoid secrets in arguments or logs. A template's hooks run with your identity and local permissions.

hooks:
  preprovision:
    shell: pwsh
    run: ./scripts/check-context.ps1
    interactive: false
    continueOnError: false
if ([string]::IsNullOrWhiteSpace($env:AZURE_SUBSCRIPTION_ID)) {
  throw 'AZURE_SUBSCRIPTION_ID is required.'
}
Write-Host "Target subscription: $env:AZURE_SUBSCRIPTION_ID"
Write-Host "Target environment: $env:AZURE_ENV_NAME"

Hook paths are interpreted in their documented project/service context. Declare the shell; a pwsh hook requires PowerShell on the machine/runner. A preprovision hook can catch missing values but does not replace authorization checks or human approval of an infrastructure diff.

CI/CD without long-lived embedded secrets

Use workload identity federation where supported. Separate deployment identities and scopes by environment, enforce production approvals, pin tool versions and inspect artifacts. Provisioning can require resource-write permission; role assignments require additional IAM authority. Do not grant Owner everywhere just to make a pipeline pass.

azd pipeline config --provider github

This command is not part of the sandbox lab and can configure repository/cloud pipeline resources. Review the generated workflow, federated identity, permissions and environment protections before accepting. --no-prompt means noninteractive decisions, not guaranteed safety; use it only when required values and approvals are already supplied.

Permissions checklist before cloud execution

The deploying identity needs subscription/group resource creation privileges and Microsoft.Authorization/roleAssignments/write at the account's scope because the lab assigns a data role. Contributor alone does not grant role-assignment authority. An administrator should provide scoped deployment and IAM authority under organizational policy. For this user-oriented lab, the principal object ID is the signed-in user's object ID, not an application/client ID.

The same identity must authenticate in both tools. azd and CLI use independent targeting configuration; compare subscription IDs and principal identities deliberately. Policy may prohibit public networks/static sites or role assignment. Do not bypass it: use an approved sandbox or study the workflow offline.

Two access surprises: disabling allowBlobPublicAccess blocks anonymous blob-container access but does not make the static website private. Also, disabling shared keys is fine because azd uses Entra data access. The storage $web container is fully owned by this azd service; a later deploy removes blobs not in the local content folder.

    principalId: principalId
    roleDefinitionId: blobDataRole
  }
}

output storageName string = storage.name
output websiteUrl string = storage.properties.primaryEndpoints.web

The stable account name fits storage naming rules. The role GUID is the built-in Storage Blob Data Contributor role; the assignment is scoped to this account. guid creates a deterministic assignment name. The module intentionally leaves principalType unspecified to accept the correct supplied principal; a reviewed production module should specify its known identity type. IAM propagation can lag behind ARM deployment completion.

Integration track / 15 minutes

Learn the boundary by diagnosing its failure.

These are rehearsal cases. Do not intentionally weaken cloud security or delete shared files to reproduce them. Explain the failing layer, evidence and minimum repair before revealing the answer.

Case 1: Bicep compiles, but role assignment creation fails

Layer: management authorization. Compilation checks syntax/schema, not the deploying identity's IAM rights. Inspect the deployment error and required roleAssignments/write action at the target account scope. Get approved scoped IAM authority or have an authorized operator manage the assignment. Do not grant broad Owner by default.

Case 2: Provision succeeded; deploy cannot find service web

Layer: azd resource discovery. Inspect the selected environment, group and resource tags. azd-service-name must equal web; confirm the account type and group outputs. Repair IaC/service configuration and reprovision, rather than selecting the first account returned by CLI.

Case 3: azd deploy returns a blob authorization error

Layer: data authorization or network access. Verify the uploader object ID, assignment scope, role and active azd identity. Allow propagation only after verifying the assignment. Inspect network rules and host connectivity. Keep shared keys and anonymous blob-container access disabled; neither is required for Entra-based upload.

Case 4: HTTP returns 404 even though resources exist

Layer: content/website configuration. Check src/web/index.html, the service's project path, successful deployment and static website settings. Confirm you use the website endpoint, not the normal blob endpoint. Resource existence does not establish uploaded content or correct routing.

Case 5: Production changed while you thought you were using dev

Layer: environment/scope and change governance. Stop, record the actual target and change evidence, and follow your incident/change procedure. Compare --environment, subscription IDs, outputs and names. Use separate scopes, deployment identities and approvals. A local environment name alone is not isolation or rollback.

Case 6: Deletion is blocked

Layer: locks, permissions or dependencies. Inspect the actual error and inventory. A lock removal is itself a consequential authorized change; do not automatically remove it. If deletion partially completes, verify remaining resources and costs, then resolve deliberately. Never broaden the cleanup target.

Beyond storage: common service inspection recipes

These are read-only command patterns for existing resources. Set the named variables to actual instances, use an explicit subscription, and check permissions. They do not create these services. Prefer IaC for lasting configuration changes.

az vm list --subscription $subscription --resource-group $rg --show-details --query "[].{name:name,state:powerState}" --output table
az vm get-instance-view --subscription $subscription --resource-group $rg --name $vmName --output json
az webapp list --subscription $subscription --resource-group $rg --query "[].{name:name,host:defaultHostName,state:state}" --output table
az webapp show --subscription $subscription --resource-group $rg --name $webAppName --output json
az containerapp list --subscription $subscription --resource-group $rg --output table
az containerapp revision list --subscription $subscription --resource-group $rg --name $containerAppName --output table
az network vnet list --subscription $subscription --resource-group $rg --output table
az network vnet subnet list --subscription $subscription --resource-group $rg --vnet-name $vnetName --output table
az network nsg rule list --subscription $subscription --resource-group $rg --nsg-name $nsgName --output table
az keyvault show --subscription $subscription --resource-group $rg --name $vaultName --output json
az keyvault secret list --vault-name $vaultName --query "[].{name:name,enabled:attributes.enabled}" --output table

The last command lists secret metadata, not secret values, and requires data-plane authorization. Avoid reading or logging secret values as a diagnostic shortcut. App runtime configuration and environment values may contain secrets; inspect only necessary fields.

Selector vocabulary: --name identifies a top-level VM/app/vault; --vnet-name identifies a parent network for a subnet; --nsg-name identifies a rule's parent security group; --vault-name selects a Key Vault data endpoint. Learn the resource hierarchy rather than assuming every command uses the same flags.
