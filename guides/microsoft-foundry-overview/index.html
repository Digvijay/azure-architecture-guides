01 / Understand

A platform.
Not just a playground.

Use Microsoft Foundry to discover models, build agents, connect knowledge and tools, and evaluate and observe the resulting application.

Model

The capability

Generates or transforms content. Choose for the task, supported modalities, tool use, quality, latency, and commercial terms.

Agent

The execution loop

Combines a model with instructions, context, and tools. Can decide what to call next; its authority must be deliberately bounded.

App

The customer experience

Your interface, business rules, user authorization, approvals, integrations, and support model still need to be designed.

Use the smallest system that works. A single model call can be enough for a fixed transformation. A deterministic workflow can be preferable when every step must follow an explicit sequence. Add an agent when adaptive tool selection creates real value.
Coming from Azure AI Foundry or Azure AI Studio?

Microsoft Foundry is the current brand. New Foundry projects and the classic hub-based experience coexist. Confirm which project, portal experience, SDK, and API your instructions target; do not combine classic Threads/Runs examples with newer Conversations/Responses examples indiscriminately.

02 / Choose

The best model?
For which task?

Catalog benchmarks narrow the field. Your own representative tasks decide what is good enough.

Task fit

Languages, modalities, structured output, tool calling, reasoning needs, context window, and supported agent integrations.

Operating fit

Tail latency, load shape, token use, deployment types, processing location, quota, version lifecycle, and recovery options.

Commercial fit

Model provider terms, licensing, pricing meters, availability, and support. Do not assume every catalog model shares the same conditions.

03 / From request to action

A tool call is a proposal.
Not permission.

  1. ReceiveAuthenticate the caller. Establish identity, tenant, intent, and permitted scope outside the model.
  2. ReasonGive the model task instructions, authorized context, and a small set of explicit tool contracts.
  3. Authorize & executeThe execution layer validates arguments, enforces policy, and obtains approval where required.
  4. Observe & stopReturn a bounded result, trace the outcome, and enforce step, time, and spend limits.

Conversation state is not truth

Messages carry context, not proof of authorization or current facts. Apply retention and deletion policies to conversation state and uploaded files.

Retries are business events

A repeated payment, ticket, or order is not harmless. Design idempotency, timeouts, retry limits, and reconciliation into side-effecting tools.

For consequential changes: separate read, propose, approve, and execute. Bind approval to the exact action and arguments, then recheck authorization at execution time.

Platform context: Agent Runtime, identity, and tools Execution controls above are application design recommendations.

03 / Knowledge and retrieval

Fresh answers.
Same access boundaries.

Retrieval-augmented generation (RAG) brings relevant knowledge into a request. It does not retrain the model or automatically enforce document permissions.

01

Prepare knowledge

Choose authoritative sources, extract and chunk content, index it, preserve access metadata, and define refresh and deletion behavior.

02

Retrieve within scope

Resolve user access and apply permission-aware retrieval before content reaches the model. Test cross-user and cross-tenant access explicitly.

03

Answer with evidence

Use retrieved context, cite sources the user can open, and allow abstention when evidence is missing, conflicting, or out of date.

RAG, fine-tuning, or a longer prompt?

Use retrieval for changing or private factual knowledge. Consider fine-tuning for repeatable behavior or style after a baseline and evaluation show a need. A longer prompt can help small, stable contexts but increases token use and does not remove access-control or freshness requirements.

Treat retrieved content as data, not authority. A document can contain misleading instructions. Keep tool authorization independent of the model's interpretation, and test indirect prompt-injection defenses.

03 / Tools, connections, and MCP

Connectivity is easy.
Trust is a design decision.

Built-in tools, custom functions, OpenAPI integrations, and Model Context Protocol (MCP) servers expose capabilities. Availability and authentication support depend on the chosen agent and tool.

Curate the surface

A Foundry Toolbox can curate and share tools through a managed MCP endpoint. Review the server owner, tool schemas, authentication, data destination, versions, and network compatibility.

Enforce the business boundary

Prefer supported Entra, managed identity, or OAuth flows. Grant only needed actions; validate all arguments and results. An MCP connection is not a security certification.

Read-only knowledge assistant

Expose search and retrieval, not write APIs. Enforce document access with the caller's authorized scope. Do not use a shared service identity with broad access as a substitute for user authorization.

Service agent that changes a business record

Separate lookup from mutation. Use narrow scopes, server-side policy, explicit approval for consequential actions, idempotency keys, and an audit record of actor, request, approval, and result.

04 / Prove

A good demo is a start.
Not a release gate.

Quality

Task completion, relevance, groundedness, citation correctness, tool choice, and argument accuracy. Inspect failures, not just averages.

Safety & access

Unauthorized retrieval, injection attempts, excessive tool authority, sensitive information exposure, and appropriate refusal or escalation.

Operations

End-to-end p95 latency, errors, throttling, token and tool use, cost per successful task, and recovery from dependency failures.

Build a versioned dataset of normal, difficult, ambiguous, multilingual, and adversarial cases. Keep a holdout set. Version the model, prompts, tool contracts, data snapshot, and evaluator configuration together.

Use deterministic checks where possible, AI-assisted evaluators where useful, and human review for business-critical judgments. Judge-model scores are measurements with limitations, not certificates.

05 / Govern

One platform.
Several trust boundaries.

Conceptual Foundry resource boundary

Resource-level governance, networking, model deployments, and scoped access.

Project: customer support

Agents, files, evaluations, and project-level permissions.

Project: operations

Separate use-case assets and access within the parent resource.

Application boundary

User identity, tenant separation, UI, API access, business policy, and human approvals.

Connected data boundary

Search, Storage, Cosmos DB, Key Vault, and business systems have their own permissions, networking, retention, and charges.

Telemetry boundary

Application Insights and logs need access controls, redaction, sampling, retention, and an incident owner.

A project is a useful development and access boundary, not a substitute for every required isolation boundary. Where policy demands separate subscriptions, resources, networks, or environments, design that separation explicitly.

05 / Network and processing controls

Private inbound.
What about outbound?

Concept explorer only. Each option represents a separately configured and verified network path, not a deployment switch.

Verify the dependency chain

Private DNS, routes, firewall rules, delegated subnets where required, private endpoints for connected resources, and tool support all matter. Test from the actual caller and agent runtime.

Decide early

Compare public egress, bring-your-own VNet, and managed VNet. Some networking choices are create-time constraints. Verify the supported configuration before provisioning.

Network isolation does not change model processing-location semantics or grant data permissions. Review all three independently: network reachability, authorization, and data handling.

05 / Identity, safety, and data governance

No single setting
makes an agent safe.

Identity & authorization

Separate developer permissions, runtime identities, and end-user authority. Distinguish management-plane from data-plane access. Scope roles and downstream permissions narrowly.

Guardrails & policy

Configure supported input, output, and agent tool controls. Test assigned policies explicitly; do not assume agent and model policies combine additively.

Information lifecycle

Classify prompts, retrieved data, files, conversation state, and traces. Agree retention, deletion, encryption, residency, and external-tool data sharing.

Do content filters enforce business authorization?

No. Detection and filtering help with covered risks; they do not prove a user can view a record or approve a transfer. Enforce permissions and business rules in the application and tool service.

Are all guardrails available for all agents and models?

No. Coverage depends on model, agent type, intervention point, and feature status. Agent content-safety guardrails and tool-call/tool-response scanning include preview capabilities. Confirm the current support matrix and test the policy actually assigned to the agent.

Can we log every prompt and tool result?

Only under an approved data-handling policy. Traces can contain personal data, secrets, or protected business content. Prefer minimum necessary telemetry, supported redaction, restricted access, and explicit retention.

05 / Reliability and economics

Count the whole task.
Not just one answer.

Illustrative assumption: each call uses 1,200 input and 300 output tokens, over 30 days. Input includes context/history for that call. No cache discount or retries assumed.

Budget the dependencies

Model tokens or provisioned capacity, hosted compute where applicable, search, tool services, storage, networking, telemetry, and evaluation calls. Apply current rates and your contract separately.

Trace end to end

Use OpenTelemetry and Application Insights integration to correlate model and tool calls. Alert on failures, latency, token growth, and quality drift.

Engineer recovery

Bound retries and loops. Test throttling, tool failures, safe degradation, rollback, and regional recovery. Alternate models and regions need their own validation.

Watch cost per successful authorized task, not cost per request alone. More tool steps can increase token use, latency, and failure exposure. Quota approval does not reserve deployable capacity.
